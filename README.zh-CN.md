# RepairScope-Bench

**当多步任务已经产生真实、持续生效的承诺，随后一步执行失败时，Agent
能否完成剩余目标，同时避免不必要地撤销此前成果？**

RepairScope-Bench v3.0 从统一、可执行的失败快照开始评测。机票、酒店、
商品、许可证和服务已经通过真实写工具创建并保存在领域数据库中。Agent
必须自行查询订单、政策、库存、合同和兼容关系，在 15 个模型轮次内执行
唯一最低增量成本的有效修复。

v3.0 只采用两个原生领域：

- 旅行：基于 STATE-Bench `TravelEnvironment`；
- 售后采购：基于 STATE-Bench `CustomerSupportEnvironment`。

评测不使用 LLM judge、主观效用权重、直接泄露最优答案的成本汇总工具、
作者手写的修复宏动作或专用 `finish()` 工具。

## 数据组成

| 维度 | 覆盖 |
|---|---:|
| 原生领域 | 旅行、售后采购 |
| 推理结构 | 10 类 |
| 每个“推理结构 × 领域”单元 | 4 题 |
| 开发集 | 40 题 |
| 测试集 | 40 题 |
| 单事实反事实对 | 40 对 |
| 每题已生效承诺 | 4 项 |
| 模型轮次上限 | 15 |

十类推理结构为：

1. 沉没成本与增量恢复成本；
2. 多跳经济影响传播；
3. 共享承诺保护；
4. 非线性价格阈值；
5. 条件合同逻辑；
6. 有可见证据的部分数量修复；
7. 桥接修复与上游替换；
8. 联合组合选择；
9. 明确期限内的持续成本；
10. 选择性切断依赖。

每类结构都在两个领域中出现，并包含两个独立情境及其反事实版本。一对
任务的用户请求、前序轨迹、失败快照和库存完全相同，只改变一个可以通过
工具查询到的政策事实；改变后，唯一最优恢复范围必须翻转。

## 客观经济目标

系统内部使用整数美分，模型看到正常的 USD 金额。失败前已经支付的历史
金额不重复计入。

```text
增量恢复成本
  = 失败后的新增付款
  + 修改费、取消费、退货费、迁移费和激活费
  + 折扣或返利追回
  - 实际退款
  - 可立即使用的抵扣和补偿
```

Oracle 枚举所有满足硬目标的原生承诺组合，计算每个恢复范围的最低可达
成本，并通过公开工具逐一重放。只有存在唯一最低成本范围，并且它相对
第二名的优势至少达到下式，任务才可发布：

```text
max($10，失败边界有效承诺总价的 1%)
```

唯一的是最终恢复范围，而不是工具调用顺序。不同合法轨迹只要达到相同
范围都可接受；模型自己造成的多余购买、取消或重复执行仍会进入真实账本。

## 模型实际看到什么

模型只收到：

- 常规旅行或售后客服系统提示；
- 用户的自然语言要求；
- 四次真实成功的前序写操作及结果；
- 最新一次真实失败调用及结果；
- 八个领域专用工具。

模型看不到硬约束 DSL、反事实配对、推理类别、变化事实指针、候选恢复
范围、全局成本汇总或 gold。决定最优范围的事实必须由模型主动查询。

## 评价指标

- `Goal Pass`：所有具有证据来源的硬目标和业务规则均满足；
- `Unique Scope Pass`：Goal Pass，且最终范围等于唯一最低成本范围；
- `Counterfactual Pair Success`：成对版本都答对，并随事实变化调整范围；
- `Incremental Recovery Cost` 与 `Cost Regret`；
- `Clean Execution`：范围正确且没有额外执行浪费；
- `Execution Waste`：多余中间操作造成的费用；
- `Over-Repair` 与 `Under-Repair`。

发布验证器还会证明评分器与 Agent 的信息对称性：624/624 条硬约束证据和
1,320/1,320 个评分状态原子都能通过模型可见的指令或结构化公开工具重放。
详见[评分器—Agent 可观测性审计](docs/OBSERVABILITY_AUDIT.md)。

范围推理与工具执行分开计分。例如 Agent 先购买错误选项、支付可查询的
取消费，随后到达正确终态，则 `Unique Scope Pass=true`，但
`Clean Execution=false`。

## 安装、构建与验证

需要 Python 3.12+ 和 Git。STATE-Bench 固定到提交
`4efcbf2d4fe60df04878859b692d9391f3d5b33a`。

```bash
python -m pip install -e .
python scripts/build_v3.py
repairscope validate data/v3
repairscope run-baselines data/v3
python -m unittest discover -s tests -v
```

当前 80 题上的确定性基线结果：

| 基线 | Goal Pass | Unique Scope Pass |
|---|---:|---:|
| 不修复 | 0 / 80 | 0 / 80 |
| 只修失败步骤 | 80 / 80 | 32 / 80 |
| 依赖闭包修复 | 80 / 80 | 36 / 80 |
| 全部撤销 | 80 / 80 | 4 / 80 |
| 只看新增标价 | 80 / 80 | 38 / 80 |
| 只追求最大退款 | 80 / 80 | 0 / 80 |
| 最少修改 | 80 / 80 | 32 / 80 |
| 精确成本 Oracle | 80 / 80 | 80 / 80 |

## 运行模型

```bash
repairscope run-suite data/v3 \
  --provider openai-compatible \
  --model YOUR_MODEL_ID \
  --base-url https://gateway.example/v1 \
  --repeats 5 \
  --output-dir results/your-model-v3
```

正式实验每题独立运行五次，同时报告 Pass@1、严格 Pass^5、反事实成对
成功率、成本 regret、是否主动调查、范围错误、执行浪费、工具错误和轮次
耗尽。服务商调用失败仍保留在分母中。

## 研究边界

v3.0 只评测统一失败状态之后的恢复。前序承诺确实由可执行工具生成，但
不是测试模型在同一回合自由选择的，因此本版本不评测失败前规划质量。
它也不评测主观偏好、随机风险或生产环境安全。

本工作的创新点不是“首次提出部分回退”，而是：在真实持久状态、可查询
政策和可审计增量成本下，确定性评测 Agent 是否选择了正确的恢复范围。
