# RepairScope-Bench

**当多步任务已经产生若干外部承诺，随后执行受阻时，Agent 能否自行探索
当前环境，找到满足剩余目标、同时避免不必要额外损失的修复方案？**

例如，Agent 已经订好上海参会的机票、酒店、接送车和会议票，最后订餐厅时
失败。把所有订单取消后重新预订，也可能完成“去上海参会”的目标，却会造成
退款损失和套餐优惠失效。本 benchmark 不只检查最终任务有没有完成，还检查
Agent 是否选择了客观损失最小的恢复范围。

当前版本为 **v0.5.1 困难集**。仓库保留原有 16 题协议原型，并新增 12 个
成组困难任务。它已经能验证评测机制，但还不是可直接支撑排行榜结论的大规模
数据集。

## v0.5 解决了什么问题

- 每题不再只有个位数候选方案：困难集有 486–729 个原始候选修复、
  18–235 个可行修复、4–30 种可行恢复范围，以及 4–30 个客观损失层级。
- 每个失败状态形成一对任务：一题只要求完成目标，另一题用自然语言要求避免
  浪费，用来分离“会完成任务”和“会选择合理范围”。
- 支持跨订单损失：修改酒店可能触发机酒套餐结算，退换电脑可能追回整套设备
  的优惠，替换冷柜可能使服务合同失效。
- 关键信息分散在订单详情、按公开类别过滤的实时库存、退款/换货报价、兼容性
  检查和套餐条款中，Agent 必须自行查询和组合；搜索结果不依赖隐藏的字符串口令。
- 使用开发、测试和机制留出三种划分，避免随机拆分近似模板。
- 正式限制是每题最多 15 轮模型交互；普通查询不消耗“修改预算”。v0.5 不向
  模型提供 `finish()`，可行任务完全根据最终环境状态评分。
- 新增 `Scope-Optimization Gap = Goal Pass - Optimal Pass`，直接衡量
  “任务完成了，但恢复范围选错了”的比例。

## 模型看到什么

所有模型从完全相同的权威失败状态开始，只看到：

1. 用户的自然语言请求；
2. 失败前已经发生的公开工具轨迹；
3. 最近一次失败调用的原始结果；
4. 可以真实查询、取消、修改和新建记录的领域工具。

模型看不到隐藏约束、Oracle、最优范围、全局损失汇总或“先优化哪个指标”的
求解提示。因此它不是从文字中选择答案，而是必须在可执行环境中调查和行动。

这是一个“给定失败边界后的条件式诊断轨道”。它刻意固定前序状态，以便公平
比较恢复范围选择能力；它不声称同时评测失败前的规划质量。端到端轨道可以作为
后续补充，但不应取代这个受控主实验。

## 客观评分

首先检查所有硬约束。对于能完成目标的方案，Oracle 按以下无权重字典序比较：

```text
(recovery_loss,
 lifecycle_cost,
 mutated_prior_commitments,
 state_changing_actions)
```

其中：

```text
recovery_loss =
    取消已有承诺后无法退回的金额
  + 恢复期间新买后又取消的浪费
  + 原地修改产生的正向净支出
  + 被触发的跨订单结算损失
```

全部指标都由交易记录和确定性规则计算，不依赖人工对“哪个方案更有价值”投票。
若多个方案的完整目标元组相同，则全部接受为 gold。

主要指标包括 Goal Pass、Optimal Pass、两者之差、额外损失、总成本遗憾、
恢复范围距离、过度回退、回退不足和工具错误。

## 三个困难任务家族

| 家族 | 失败前已经生效的承诺 | 新失败 | A/B 最优范围变化 |
|---|---|---|---|
| 上海参会 | 往返机票、酒店、接送车、会议票 | 餐厅满员 | 保留酒店，仅补餐厅 / 更换酒店并承担套餐结算 |
| 放射科工作站 | 电脑、显示器、安全密钥、保修、软件 | 扩展坞不兼容 | 增加通用扩展坞 / 联动更换电脑、保修和软件 |
| 诊所冷链 | 冷柜、传感器、网关、服务、安装 | 电池缺货 | 增加兼容电池 / 联动更换冷柜和服务合同 |

每个 A/B 对只改变一个关键库存或兼容性事实，失败文本保持相同，但 Oracle
最优恢复范围必须改变。

困难集还设置了自动质量门槛。每个损失敏感任务至少需要：

- 100 个原始候选修复；
- 8 个满足硬目标的修复；
- 4 种可行恢复范围；
- 3 个不同的恢复损失层级。

## 基线结果

| 策略 | 完成目标 | 达到最优 |
|---|---:|---:|
| 不修复 | 0 / 12 | 0 / 12 |
| 只处理失败槽位 | 0 / 12 | 0 / 12 |
| 只处理声明受影响的步骤 | 0 / 12 | 0 / 12 |
| 全部回退后重建 | 12 / 12 | 0 / 12 |
| 忽略已有损失，寻找最终总价最低方案 | 12 / 12 | 6 / 12 |
| 穷举损失感知 Oracle | 12 / 12 | 12 / 12 |

这正是 benchmark 想要的区分：一种策略可以 100% 完成任务，却 0% 选择正确
恢复范围。

## 安装与验证

```powershell
python -m pip install -e .
python scripts/build_pilot.py
python scripts/build_challenge.py
repairscope validate data/pilot
repairscope validate data/challenge
python -m unittest discover -s tests -v
repairscope run-baselines data/challenge
```

正式模型实验默认每题独立运行 5 次，最多 15 轮，同时报告 Pass@1 和严格
Pass^5。单次运行只能作为连通性测试。

## 研究边界

本文不能宣称“首次提出部分回退”。部分回退、补偿事务和恢复范围早已存在。
更稳健的创新表述是：

> 首次面向现代工具 Agent，受控、可执行地评测其在已有外部承诺和客观额外
> 损失下的恢复范围选择能力。

当前版本已经修复了原型“题目太小、工具信息太直接、完成目标与范围最优无法
分开”的问题。若要达到顶会完整论文规模，仍需更多独立领域、更大的隐藏测试集、
第二套 Oracle 复核以及多模型正式实验。
